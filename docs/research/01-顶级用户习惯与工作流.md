# 01 · 顶级用户习惯与工作流（含：如何借 AI 反而变强）

> 覆盖方向 1（习惯共识）+ 方向 7（编程与架构能力提升）

## TL;DR

1. 前 1% 用户与普通用户的分水岭不在"会不会写提示词"，而在**是否把 AI 当系统来经营**：规则文件、记忆文件、文档驱动、子 Agent 委派、定时任务编排是五件套。
2. Anthropic 官方把这套东西命名为**上下文工程**：上下文是有限资源，会"腐烂"；一切优化的目标是"最小高信号 token 集"。
3. Karpathy 的工作流在几周内从"80% 手写 + 20% Agent"翻转为"80% Agent + 20% 润色"，他称之为 20 年编程生涯最大变革——但他同时指出 90% 的 AI 编码费用浪费在"发送了不需要的上下文"上。
4. 想借 AI 变强而不是变弱：Anthropic 实验证明**"概念提问型"用法**（只问概念、自己写码）技能得分最高（平均 86%），整包委托型最差；AI 应该当解释器，当代码生成器。
5. 国内顶级实践者（歸藏）的日常：睡前给 AI 布置凌晨定时任务、70% 时间做调研与计划文档、三个核心文档（宪法/路由/护栏）治理整个项目，本人一行代码不写。

## 一、共识一：上下文工程取代提示词工程

Anthropic 工程博客《Effective context engineering for AI agents》（2025-09-29）是目前最权威的一手定义：

- **上下文腐烂（context rot）**：随着上下文 token 增多，模型准确回忆信息的能力下降——所有模型都存在，只是程度不同。
- **注意力预算**：n 个 token 产生 n² 注意力关系，上下文越长注意力越稀薄；上下文必须被当作"边际收益递减的有限资源"。
- 核心公式：**找到最小的高信号 token 集合，最大化期望行为的出现概率**。
- 系统提示词要写在"合适的高度"：一端是脆弱的 if-else 硬编码，另一端是假共享上下文的空泛指令，正确的位置在中间。
- 三大长时程技术（原文细节）：
  1. **Compaction（压缩）**：Claude Code 把对话史交给模型总结，保留架构决策、未解决 bug、实现细节，丢弃冗余工具输出，再带上最近访问的 5 个文件重启上下文。
  2. **结构化笔记（Agentic Memory）**：Agent 定期把笔记写到上下文之外的文件（NOTES.md、todo list），之后拉回。Claude 打 Pokémon 的案例显示：无人工提示的情况下，Agent 自己发展出地图记录、成就清单、战斗策略笔记，从而支撑数小时的长程任务。Sonnet 4.5 发布时官方同步推出了基于文件的 memory 工具（公测）。
  3. **子 Agent 架构**：主 Agent 只管高层计划，子 Agent 用"数万 token"的独立上下文深挖，只回传 1000–2000 token 的蒸馏摘要——详细的探索过程被隔离在子 Agent 内部，主 Agent 保持干净上下文专注综合。

来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## 二、共识二：规则文件（CLAUDE.md / AGENTS.md）是"个人操作系统的内核"

- Claude Code 官方文档明确了项目记忆机制：CLAUDE.md 存放项目约定，支持项目级/用户级/企业级分层（https://code.claude.com/docs/en/memory）。
- Karpathy 的观察被开发者 Forrest Chang 提炼为 **65 行 CLAUDE.md 的四大准则**，实测把编码准确率从 65–70% 提到 91–94%，两仓库合计 22 万+ Star，是 GitHub 增长最快的单文件项目：
  1. **编码前先思考**：明确陈述假设；不确定就问；多种解释就列选项；发现更简单方案主动推荐。
  2. **极简优先**：不加没要求的功能；一次性代码不抽象；50 行能搞定不写 200 行。
  3. **外科手术式修改**：不顺手优化旁边代码；不动无关格式；每行改动都能追溯到需求。
  4. **目标驱动执行**：与其说"修复认证问题"，不如说"写一个复现 bug 的测试→让测试通过→确认无回归"。Karpathy：LLM 非常擅长"循环直到达成特定目标"。
  - 实测数据（社区报告）：融资技能 70%→94%、MEDDIC 销售 65%→91%、Shopify 模板渲染快 53%、Claude 错误率 41%→3%；应用准则后生成代码量减少 30–40%。
  来源：https://cloud.tencent.com/developer/article/2672609
- 社区已出现把规则文件当 npm 包管理的实践（`base-agent-rules`，可复用于 Codex 与 Claude Code：https://www.npmjs.com/package/base-agent-rules）。

## 三、共识三：多 Agent 委派 + 定时任务 = "一家公司"的雏形

- Claude Code 官方已内建"用动态工作流大规模编排子 Agent"（https://code.claude.com/docs/en/workflows）；Anthropic 的 AI-Native SDLC playbook 把"需要人审批的 gate"放到部署阶段而非编码阶段（https://claude.com/blog/the-ai-native-sdlc-playbook）。
- 国内播客《What's Next｜科技早知道》S10E18《1 人公司，扛 5 个人的活，还要管 50 个 Agents》直接以实践者视角讨论这种组织形态（https://podscan.fm/podcasts/whats-nextke-ji-zao-zhi-dao/episodes/1-ren-gong-si-kang-5-ge-ren-de-huo-hai-yao-guan-50-ge-agents-s10e18）。
- 典型一夜编排（歸藏）：睡前给 Codex 和 Claude Code 布置定时任务，凌晨 5 点开跑；任务拆成 10 个 pass，一晚全部做完，自动调用 MCP、跑测试、做 smoke test；起床直接拿到可测试的版本。
  来源：https://www.163.com/dy/article/KSNFVMK60511B6FU.html

## 四、共识四：个人知识库喂给 AI（第二大脑 → Agent 记忆）

- Karpathy 的 "LLM Wiki" 模式已催生开源复刻：`llm-wikid`（"Clone, run Claude Code, start building your second brain"，https://github.com/shannhk/llm-wikid）、`second-brain`（LLM-maintained personal knowledge base for Obsidian，https://github.com/NicholasSpisak/second-brain）。
- 思路统一：知识库从"人检索"变成"Agent 维护 + Agent 检索"；人只负责定调与审核。
- 歸藏的内容流水线即为此形态：skills 自动爬取他常看的 newsletter/网站/邮件，结合日程生成报告；他自己刷 X 做信息源；长内容交给 AI 全流程，人只完成第一步"给上下文定调"。

## 五、人物侧写：顶级用户的一天（以歸藏为例，全部一手访谈）

来源：真格基金 Token Grant 访谈（https://www.163.com/dy/article/KSNFVMK60511B6FU.html）+ 2025 年度回顾（https://m.163.com/dy/article/KI24JDV30556BM3X.html）

- **身份**：前大厂 UI/UX 设计师 → 超级一人公司（CodePilot 作者、Medeo 顾问、9 平台自媒体、2000 人付费社群）。
- **量化习惯**：单月最多消耗 7600 万 token；CodePilot 累计生成 30 万+ 行代码、保留 11 万行；几百个 commit 里 47% 是 fix——他认为"核心问题不是 token 数量，而是单位 token 解决多少问题"。
- **文档驱动开发**：整个开发流程全部文档化，三个核心文档 = ① Claude Code 文档（"AI 的宪法"：什么绝对不能做/必须做）② 目录路由文档（全部文档的入口和结构）③ 护栏文件（保护两样东西：上下文与接口；接口损坏属 P0）。
- **时间分配**：约 70% 时间在调研——和 AI 讨论技术方案、反复审核计划文档，然后才让 AI 按文档执行；"你计划得越细，后面出问题的概率就越小"。
- **他给 AI 的三个边界**：AI 不知道用户真实运行环境（默认世界只有 macOS）；AI 的领域知识会过时（"最可怕的不是它不知道，是它以为自己知道"）；AI 不知道什么是好的——决策永远是人做，"它只需要给我足够的信息"。
- **三大底层能力**（他的原话）：主观能动性、学习能力、品位——品位是"过去学习、工作、内容消费沉淀在身体里的审美和判断"。

## 六、方向 7：AI 结对编程——如何变强而不是退化

### 6.1 证据：错误用法确实导致技能退化

Anthropic 研究《How AI assistance affects coding skill》（2026 初发布，arXiv:2601.20245）：

- 实验对象学习小众 Python 异步库 Trio，AI 组技能测验平均低 4.15 分（满分 27）；
- **调试能力差距最大**：无 AI 组平均遇到 3 个错误，AI 组只遇到 1 个——错误本身是学习的原料；
- AI 组任务完成时间并不显著更短（有人单次查询耗 6 分钟）。
- 来源：https://www.anthropic.com/research/AI-assistance-coding-skills ；中文报道 https://www.36kr.com/p/3698501463371652

### 6.2 六种用法，三种退化、三种保持

| 退化型 | 保持型 |
| --- | --- |
| ① 整包委托（最快、得分最低） | ④ 生成后理解型：先让 AI 生成，再追问原理 |
| ② 渐进依赖：越难越交出去 | ⑤ 混合解释型："生成代码，并解释为什么这样实现" |
| ③ 迭代调试者：粘报错要答案 | ⑥ 概念提问型：只问概念，自己写（平均得分 86%，速度不慢） |

**共同点：保持认知参与度。把 AI 当解释工具，而非代码生成器。**

### 6.3 顶级用户的"反退化"姿势汇总

- Karpathy：从"Vibe Coding 抬高了地板"进化到"真正的战场是精确控制 AI 的行为边界"；工具链为 Cursor 主力 + GPT-5 备用四层结构（https://eu.36kr.com/en/p/3438162927701383）；"Software 3.0"演讲主张人主导意图、机器主导实现（https://www.163.com/dy/article/K2H387HF0511PEBT.html）。
- Ethan Mollick（沃顿，《Co-Intelligence》作者）：学生把 AI 当拐杖则什么也学不到（https://elpais.com/tecnologia/2024-10-03/ethan-mollick-analista-los-estudiantes-que-usan-la-ia-como-muleta-no-aprenden-nada.html）；他 2026 年的新建议中心是"让 AI 干活、让人当审稿人"（https://beginnersinai.org/ethan-mollick-ai-guide/）。
- 社区对照研究《Fast and Forgettable》同样发现新手在 AI 辅助下完成任务更快、但学习与情绪投入更差（https://dl.acm.org/doi/full/10.1145/3765964.3811664）。
- 中文社区的自省文章《AI 写代码，脑子却空了》获得大量转发，说明"退化焦虑"已成本行业共识议题（https://cloud.tencent.com/developer/article/2667713）。

### 6.4 系统设计学习法（给用户的可操作建议）

1. **先读 AI 产出的代码再采纳**：把"生成后理解型"固化为习惯——每段新代码至少追问一次"为什么这样实现"。
2. **学习新技术时切到"概念提问模式"**：问原理、问权衡、问反例，自己动手写；保留踩错机会。
3. **让 AI 出题而不是给答案**：系统设计学习（如"设计一个 TapTap 级别的游戏分发后端"）先自己写方案，再让 AI 挑刺，模拟评审会。
4. **用 CLAUDE.md 固化个人工程准则**：直接借鉴 Karpathy 四准则，再逐月补充自己的"踩坑条款"。
5. **重要 bug 先自己定位 15 分钟**，再让 AI 复核——保住调试能力（退化最重的正是这块）。

## 七、对用户的落地意义

- 你（游戏开发者 + 科创 + 学产品/投资）最适合的不是"换个更聪明的模型"，而是**把自己的工作目录变成一个有宪法、有记忆、有护栏的系统**：游戏仓库放 CLAUDE.md（美术规范、代码规范、禁止事项），学习笔记库放 AGENTS.md（如何检索、如何总结），创业项目放 PRD 模板与竞品库。
- 你的五个 AI 使用场景（游戏、AIGC、产品、投资、tutor）可以共用同一套"上下文工程"底座——这正是后续《首批可落地行动清单》第一组行动的依据。
